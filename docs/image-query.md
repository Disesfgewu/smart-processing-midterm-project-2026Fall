# 以圖找圖（image-guided detection）實驗：數據與報告素材

> 實驗日期：2026-11-10　裝置：Jetson Orin Nano（MAXN_SUPER (nvpmodel 2)），OWL-ViT base patch32（TensorRT fp16 引擎），影像長邊縮到 1280。
> 原始資料：`data/bench/jetson/image_query.json`（160 筆實驗紀錄＋摘要＋負對照）；本檔的表格由腳本從該 JSON 計算，非手抄。
> 重現：`.venv-jetson/bin/python benchmark/bench_image_query.py`（約 35 秒）。真值與影像清單：`benchmark/confidence_cases.json`。
> 網頁互動版（第 7 節）的原始資料：`image_query_api.json`、`image_query_robust.json`、`image_query_api_bigimage.json`（同在 `data/bench/jetson/`），腳本 `benchmark/bench_image_query_api.py`、`bench_image_query_robust.py`。

## 1. 結論（可直接寫進報告的版本）

1. **在這批工業零件影像上，以圖找圖明顯比文字查詢更能把「同類的其他零件」排到前面。** 電路板的電容：文字查詢的 P@m 為 0.00，用範例圖 inplace 為 0.83（1-shot）；電感：0.00 → 1.00。AUC 從 0.71–0.79 升到 0.87–0.95。這是**排序**的改善。
2. **但它不能解決「信心分數低」，也不是可校準的信心。** 影像查詢的分數會飽和：inplace 模式下，電路板上幾乎所有零件（電感、線圈、IC）的分數都在 0.95 以上，最高負例平均分（0.97–0.99）反而高於真物件平均分（0.81–0.88）。絕對分數不能拿來當「這是不是同類」的機率，只能用排序。
3. **效果依賴範例怎麼取：** `inplace`（用目標圖自己在範例框位置的特徵，等同於使用者在畫面上點選一個物件）最好；`crop`（把範例裁出來單獨編碼，可以跨圖使用）較弱，且**很依賴選到哪個實例當範例**（電容 1-shot P@m 範圍 0.00–0.83）。
4. **推論成本：「範例固定」時幾乎不變；網頁流程每次請求都重算範例，且框數多時很慢（見 7.4）。** 查詢特徵換範例時算一次（約 50–60 ms，與文字編碼相同量級），每張影像的 OWL 推論中位數文字 39.6 ms、crop 38.9 ms、inplace 35.9 ms（差異在量測雜訊內）。
5. **`crop` 對影像雜訊很敏感（7.5），`inplace` 穩定；網頁預設用 `inplace`、範例門檻預設 0.95（7.3）。**
6. **限制很大（寫報告時必須同時寫出）：** 只有 4 張圖、5 個可評估的概念、真值為目視估計；`inplace` 只適用於「範例就在要搜尋的那張圖裡」；跨圖的負對照顯示 `crop` 會在沒有該物件的圖上給出最高 0.32–0.38 的分數（inductor 的真物件平均分只有 0.05），**無法設定通用門檻**。

## 2. 方法

- **實作**：`src/pipeline.py` 的 `OpenVocabSegmenter.set_image_queries(exemplars, mode, with_text)`，新增方法，原本的文字流程（`set_prompts`）沒有改動。NanoOWL 的 `decode()` 只看「查詢向量」，所以把範例物件的 OWL class embedding 放進去取代文字向量即可，不需要改模型或重建引擎。
- **範例特徵怎麼取**（沿用 HF `OwlViT.image_guided_detection` 的做法）：把範例影像丟進 OWL 取得每個 patch 的預測框與 class embedding，挑與範例框 IoU 最高（≥ 最高值的 0.8 倍）的一批，其中取「與整張圖平均 embedding 最不相似」者（最有辨識度）。
- **兩種模式**：`crop`＝把範例框單獨裁出、補成正方形再編碼（範例可來自別張圖，但物件在裁切裡占滿畫面，與目標圖尺度不同）；`inplace`＝直接用範例所在整張圖的 patch 特徵（尺度與目標一致，範例影像必須就是被搜尋的影像）。
- **融合**：`text+crop` 對每個概念同時放文字查詢與影像查詢，同概念取最高分（與 HyDE 多描述的歸併方式相同）。多個範例（k-shot）同理取最高分。

## 3. 實驗協定

- **只評估同一張圖裡有 n ≥ 2 個實例的概念**：cats 的 cat／remote control、電路板的 capacitor（7）／inductor（3）、焊接圖的 steel pipe（2）。單一實例的概念（person、overhead crane、toy rocket、spindle motor、spring）在同圖內沒有「其他實例」可找，**不能用這個協定評估**（其中 spring 與 inductor 正是文字查詢完全失敗的案例，spring 因此沒有數據）。
- **留 k 個當範例、找剩下的**：k＝1、2，所有組合；評分時**排除範例本身**（與範例框 IoU ≥ 0.3、或偵測框有一半以上落在範例框內者一律丟掉，後者是範例物件的子框），文字基準也套用同樣排除，兩邊公平。
- **正例**＝偵測框與「其他」同概念真值框 IoU ≥ 0.5。每次只查單一概念；只要框（不跑 SAM）。
- **指標**：m＝剩下的目標實例數。**P@m**＝分數最高的 m 個偵測中有幾成是正例；**AUC**＝隨機抽一個正例與一個負例，分數把正例排前面的機率（0.5＝沒資訊）；**名次中位數**＝每個目標實例第一個匹配偵測在排序中的名次（1＝最前）；**最高負例分**＝排除範例後最高分的非正例。表中數字是對所有範例組合取平均。
- **負對照**：用範例（第 0 個實例）去搜「沒有該概念」的其他圖，記錄最高分；`inplace` 不能做（特徵取自範例所在圖）。

## 5. 觀察（附疊圖）

- `data/bench/jetson/confidence_overlays/image_query_inplace_capacitor_ex0.png`：以電路板一顆小銀色電容為範例（紅框）、inplace 模式；藍框是真值、綠框是 ≥ 0.3 的偵測。四顆小銀色電容與兩根深色高電容都拿到 0.97–1.00，**但方形電感（0.95–0.98）、銅線圈（0.97）、黑色 IC（0.96）也同樣 ≥ 0.95**。可見影像查詢學到的是「這張圖裡這類看起來像零件的東西」，分數之間只差 0.03–0.05，排序能用、數值不能當信心。
- 這與最初的問題（「信心都在 0.01–0.1」）的關係：以圖找圖把電路板零件的真物件平均分從 0.002–0.007（文字）拉到 0.05–0.34（crop）與 0.81–0.88（inplace），**數字變大了，但可靠度沒有等比例變好**——負例也一起變大。若報告要談「提升信心」，應主張「排序變準」，而不是「信心分數變高」。

## 6. 限制與資料更正（誠實揭露）

- **規模**：4 張圖、5 個可評估概念、每個概念 2–7 個實例。**沒有統計顯著性**，P@m 以少數幾個 run 平均。
- **真值是目視估計**（誤差約 ±15 px），不是標註資料集。`steel pipe` 的兩個「實例」其實外觀差異大（法蘭鋼管與直立圓筒），真值不可靠，所有查詢方式 P@m 都是 0，**不應拿來下結論**。
- **真值更正**：第一次跑時電路板漏標了上方 2 根深色高電容（真值為 5 個電容），被當成負例而高估了假警報；2026-11-10 看疊圖後補標（改為 7 個）並重跑，本檔數字是更正後的。補標前後的定性結論相同（inplace > crop > text）。這是看過結果後才修的標註，已揭露。
- **排除規則也調整過一次**：原本只排除與範例 IoU ≥ 0.3 者，後來加入「一半以上落在範例框內」，結果幾乎沒變，所以高分負例不是範例子框造成的。
- **inplace 的適用範圍**：範例必須就是被搜尋的那張影像（使用者在畫面上點選一個物件）。拿它去搜別張圖沒有意義，所以沒有負對照。實際產品若要「上傳範例圖去搜別的影像」，只能走 crop，而 crop 較弱且不穩（見 4.3、4.4）。
- **縮圖**：影像長邊縮到 1280，與伺服器預設（3072–4096）不同，沒有量測縮圖大小的影響。
- **只測了 OWL-ViT base patch32**（文字與影像查詢共用同一個模型）；沒有測 patch16 / OWLv2，也沒有測 spring（單一實例）。

## 7. 網頁上的「點選一個框當範例」：實作與 API 實測（2026-11-10 補）

### 7.1 做了什麼

- **後端**：`POST /api/segment` 新增選用參數 `exemplar_box`（JSON `[x0,y0,x1,y1]`，**占整張圖寬高的比例 0~1**，所以不受伺服器縮圖影響）、`exemplar_mode`（`inplace` 預設／`crop`）、`exemplar_with_text`。給了 `exemplar_box` 時 `prompts` 必須只有 1 個（範例所屬的概念），HyDE 不套用；回應多了頂層 `exemplar`（模式與框）和每個偵測的 `exemplar`（是否就是被點選的範例本身）。`SegmentService.run(..., exemplar=...)`。
- **快取失效**：影像查詢結束後把 `seg.prompts / groups / text_encodings` 清空。原本的快取判斷是 `seg.prompts == prompts`，不清空的話，下一個同名的文字請求會誤用範例特徵（相機執行緒也會）。有回歸測試（7.2）。
- **前端**（`frontend/app.js`、`index.html`）：圖片模式下，點結果畫面上的任何一個框（沒開遮罩時用框命中、取面積最小者）→ 以它為範例用同一張圖重新偵測；新增「以圖找圖」模式下拉（原位／裁切）、**「範例門檻」滑桿**（預設 0.95，範圍 0.5–0.999）、結果卡上的說明列與「清除範例，回到文字查詢」。範例標記 `◎`。換圖會清除範例。
- **為什麼要獨立的範例門檻**：原本的「偵測門檻」滑桿最高 0.9，而影像查詢的分數大多在 0.95 以上（見 4.5、5 節）；用預設 0.1 會回傳約 290 個框，且每個框都要跑 SAM（見 7.4，開遮罩要 7 秒）。預設 0.95 是依 7.3 的掃描挑的折衷，不是最佳值，沒有單一最佳值。

- **和 4.5 的「成本不變」要分開看**：4.5 是「範例固定、之後每張影像的推論」；網頁流程是**每次請求都重算範例特徵**（一次額外的 OWL 影像編碼，約 47–57 ms 的查詢設定時間），所以不算遮罩時從文字的 113 ms 增加到 159 ms（門檻 0.95、8 個框）。

### 7.5 穩定性：同一張圖只改 JPEG 重新壓縮品質（`benchmark/bench_image_query_robust.py`）

我先在 API 實測時發現：經 JPEG q92 上傳後，`crop` 的結果和離線實驗差很多（cats 右邊那隻貓的分數 0.793 → 0.444），改用 PNG 上傳後與離線一致，才確定是影像雜訊造成。再系統性量測（1-shot、14 組範例：cats 4、電容 7、電感 3；每格 P@m／目標實例平均分）：

| 模式／挑選規則 | 品質 orig | 品質 99 | 品質 95 | 品質 92 | 品質 85 | 分數標準差（跨品質） |
|---|---|---|---|---|---|---|
| inplace／distinct（預設） | 0.92／0.98 | 0.93／0.97 | 0.87／0.98 | 0.93／0.97 | 0.92／0.97 | 0.006 |
| inplace／best_iou | 0.75／0.93 | 0.73／0.93 | 0.74／0.94 | 0.75／0.93 | 0.83／0.93 | 0.029 |
| inplace／mean | 0.89／0.94 | 0.88／0.93 | 0.87／0.94 | 0.84／0.92 | 0.86／0.93 | 0.015 |
| crop／distinct（預設） | 0.57／0.30 | 0.48／0.26 | 0.42／0.22 | 0.62／0.24 | 0.45／0.18 | 0.065 |

- **`crop` 對雜訊很敏感，`inplace` 穩定得多**：同一張圖，crop 的目標平均分標準差 0.057–0.096，inplace 的 distinct 只有 0.006；cats 單例的例子：crop 的另一隻貓分數 q99 為 0.456、q95 為 0.066，而 inplace 都在 0.93–0.99。
- **我原本的假設不成立**：我懷疑是「挑與全圖平均最不像的 patch」這個規則（`distinct`）不穩，所以加了 `select` 參數比較 `best_iou` 與 `mean`。結果三種規則在 crop 下都一樣不穩，`inplace` 下 `distinct` 反而最好最穩，所以**保留預設 `distinct`、沒有改程式的行為**。不穩的原因是 crop 把範例單獨裁出再編碼（範例本身的特徵對壓縮雜訊敏感），不是挑選規則。
- **對使用的意義**：網頁圖片模式送的是使用者的原始檔（沒有再壓縮），所以 `crop` 在網頁上看到的是「乾淨」的結果；但只要影像經過重新壓縮或縮放（例如攝影機影格、手機轉傳），crop 的結果就不可預期。**inplace 不受這個影響。**

### 7.6 限制與沒做的事

- **前端沒有在真實瀏覽器裡操作過**：這台沒有自動化瀏覽器，沒有可用的 node。我做的是：`app.js` 的語法檢查（原版與新版都能被 ES2017 解析器解析，已先把原本就有的 `?.`、`??`、`catch {}` 在暫存副本換掉）、新元素 id 與 `index.html` 的對照、伺服器確實提供新的 HTML／JS，以及用與前端完全相同的參數打 API。**點選的命中判斷、滑桿連動、說明列的排版與顏色都沒有目視確認**，請在瀏覽器實際點一次。
- 範例只用一個、只對圖片模式、只對單一概念；多概念混合（有的用文字、有的用範例）、影片／攝影機模式、`exemplar_with_text` 的前端入口都沒有做（後端參數有，沒有掃描數據）。
- 掃描與延遲只有電路板（以及 cats 的準確度）一張圖的數據；`steel pipe` 與單一實例的概念（含 spring）仍沒有數據。
- 這些量測用的伺服器是 `PORT=8123 HOST=127.0.0.1 python -m server.main`（TensorRT，SAM＝nanosam）；跑完後我已停掉。
